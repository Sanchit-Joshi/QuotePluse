# Decision Log

Format: ADR-NNN | Date | Decision | Why | Alternatives considered

## ADR-001 | 2026-07-25 | Web app replaces Excel-to-PDF workflow
**Decision:** Build a Next.js + PostgreSQL web app that generates PDFs from a fixed HTML/CSS template with dynamic data, rather than continuing to script/automate Excel.
**Why:** Excel workflow has no history, no numbering discipline, manual arithmetic risk, and doesn't scale to multiple users/devices.
**Alternatives:** Keep Excel + macro automation (rejected — doesn't solve history/search/validation); Google Sheets + Apps Script (rejected — same core limitations, weaker type safety and testing).

## ADR-002 | 2026-07-25 | Tax model: India GST for MVP
**Decision:** MVP implements CGST/SGST/IGST split, GSTIN, HSN/SAC fields as first-class, not a generic tax percentage.
**Why:** User confirmed India GST is the actual business requirement; building generic-first would require rework to add compliant GST math later.
**Alternatives:** Generic single-rate tax (deferred to future-roadmap as a config option, not built now).

## ADR-003 | 2026-07-25 | No authentication in MVP
**Decision:** MVP ships single-user, no login screen. Architecture keeps a `userId`-ready shape (nullable/default single-tenant) so Better Auth/Clerk can be added without schema rewrites.
**Why:** User confirmed single-user usage for now; auth adds upfront complexity that isn't the bottleneck (PDF/quotation flow is).
**Alternatives:** Ship Better Auth from day one (deferred — see future-roadmap.md).

## ADR-004 | 2026-07-25 | Deployment target: local Docker Compose first
**Decision:** Primary deployment path exercised and verified is `docker-compose up` on the client's machine. Cloud deployment guides (Railway/Render/DigitalOcean/AWS/Azure) are written per the spec but not live-tested in this phase.
**Why:** User confirmed local usage is the actual current need.
**Alternatives:** Deploy to a cloud host now (deferred until user picks one).

## ADR-005 | 2026-07-25 | PDF template: default professional layout first, pending client's real template
**Decision:** Build and ship a first professional GST-invoice-style HTML/CSS template now; swap in the client's exact Excel/PDF layout once supplied, without changing the underlying data model or API contract.
**Why:** User has not yet supplied the reference file; blocking all work on it would stall the whole project. The data layer (customer/items/totals/tax) is independent of the visual layout, so this is safely reversible.
**Alternatives:** Wait for the file before writing any code (rejected — unnecessary serialization of independent work).
**Follow-up:** Revisit immediately when client file arrives; see [known-limitations.md](known-limitations.md).

## ADR-006 | 2026-07-25 | Document numbering: DB sequence with transactional allocation
**Decision:** Quotation/invoice numbers are allocated via a per-document-type counter row updated inside the same transaction that creates the document. A rolled-back transaction may burn a number (gap), but two documents can never receive the same number.
**Why:** Correctness (no duplicate numbers on a legal/financial document) matters more than perfectly gapless numbering; true gapless sequencing under concurrent writes requires heavier locking that isn't justified for a single-user MVP.
**Alternatives:** Postgres `SERIAL`/sequence per type (simpler but harder to reset yearly per FR-7.2); application-level locking with retry (more complex, deferred unless multi-user contention becomes real).

## ADR-007 | 2026-07-25 | PDF generation: Playwright prints the live preview page, not a react-dom/server render
**Decision:** `PdfService` has Playwright navigate to the app's own `/quotations/:id/preview` (or `/invoices/:id/preview`) route and calls `page.pdf()` on it, rather than calling `renderToStaticMarkup(<DocumentTemplate/>)` out-of-band and feeding the HTML string to `page.setContent()`.
**Why:** Next.js's App Router refuses to bundle any module reachable from a Route Handler that imports `react-dom/server` ("You're importing a component that imports react-dom/server... render or return the content directly as a Server Component instead") — this broke the original design in `architecture.md` §PDF generation. Navigating Playwright to the real, already-working preview page sidesteps the restriction entirely and *improves* the WYSIWYG guarantee: the PDF is now a print of the exact page a user can see in-browser, not a second parallel rendering path that could silently drift from it.
**Consequences:** The app's chrome (sidebar, header, preview toolbar) is hidden via `print:hidden` classes (`AppShell`, `PreviewToolbar`) so only `DocumentTemplate` prints. `PdfService` requires the Next.js server to be reachable at `APP_URL` (default `http://localhost:3000`) from within its own process — trivially true in Docker (Playwright runs in the same container) and in local dev.
**Alternatives considered:** Move PDF routes to the legacy Pages Router (`pages/api/*`), which doesn't carry the same restriction — rejected as an unnecessary second routing system for one endpoint. Render via a headless React renderer other than `react-dom/server` (e.g. `satori`) — rejected as unnecessary added dependency when the live page already renders correctly.

## ADR-008 | 2026-07-25 | MVP declared production-ready; core loop verified end-to-end
**Decision:** The MVP (customers, products, quotations, invoices, PDF generation, dashboard, settings) is considered feature-complete for this pass. Verified via: 87 passing unit/integration tests (73.86% statement coverage, concentrated on the totals engine and document state machines), 1 passing Playwright E2E test, `npm run lint`/`npm run typecheck`/`npm run build` all clean, and a manual full-lifecycle test run **inside the actual production Docker image** (`docker compose up --build`) — created a customer, created and finalized a quotation, downloaded a real PDF (verified `%PDF-` header and valid page count via `file`), confirmed structured JSON logs (request/audit/pdf categories) appeared correctly, and confirmed Postgres migrations applied automatically via `docker/entrypoint.sh`.
**Why:** A Docker build succeeding is not the same as the containerized app actually working — Playwright/Chromium in particular has a history of breaking in slimmed-down containers (missing shared libraries). Running the golden path against the real container (not just `docker build`) is the only way to be confident PDF generation works in the deployed artifact, not just in local dev.
**Follow-up:** See [known-limitations.md](known-limitations.md) for what's explicitly deferred, and [future-roadmap.md](future-roadmap.md) for what's next.

## ADR-009 | 2026-07-25 | PDF template and tax formulas rebuilt to match the client's real reference invoices
**Decision:** The client supplied two real invoices (`SAI2526000049 SBI BETAWAD FRFC.xlsx`, `SBI Nandurbar.xlsx`) generated from their actual Excel workflow. We read both workbooks cell-by-cell (values, formulas, borders, fonts) and rebuilt `DocumentTemplate`/`styles.ts` and `TotalsCalculator` to match exactly, superseding the placeholder design from ADR-005. Concretely:
- **Visual layout**: plain white background, black text, medium black borders around every section (company block, header-info box, item table, totals box) — not the earlier dark-header-row design. Company block, GSTIN line, centered document title, two-column "To, / doc meta" header, `SR.NO | Product Description | HSN/SAC | Qty | Rate Each | Amount` table, VENDOR CODE + bank details bottom-left mirroring a bordered Subtotal/CGST/SGST/Total box bottom-right.
- **Tax formula**: their sheet computes `Amount = Qty * Rate` per line, then `CGST = Subtotal * 9%` and `SGST = Subtotal * 9%` as single multiplications on the whole taxable value — not a sum of per-line-rounded tax amounts. `TotalsCalculator` now groups line items by GST rate and taxes each group's combined taxable value once, which is arithmetically identical to their formula for the single-rate case (their real invoices) and generalizes correctly if a document ever mixes rates.
- **No rupee rounding**: their invoices show exact rupee.paise amounts (`numfmt: '0.00'`), never a "Round Off" line. Removed the "round grand total to nearest rupee" step that ADR-005's placeholder had assumed; `roundingPaise` is now always `0`.
- **New fields**: `Customer.referenceCode` (their "VENDOR CODE-RAJE5945734" — a code *the customer* assigns to us, constant per customer relationship) and `QuotationLineItem.hsnSac` / `InvoiceLineItem.hsnSac` (their invoices show one HSN code per document; we capture it per line for correctness — a multi-product invoice can legitimately have mixed HSN codes — and the template shows a single header "HSN CODE - xxxx" line only when every line happens to share one code, otherwise falling back to a per-line column).
**Why:** "Copy the client's exact formulas" is a correctness requirement, not a style preference — GST tax computation errors on a legal invoice are a serious failure mode, and the client explicitly asked for their real math to be replicated, not our own interpretation of "how GST invoices usually round."
**Verification:** Two golden-master unit tests (`totals-calculator.test.ts`) reproduce both reference invoices' exact subtotal/CGST/SGST/total figures. A quotation seeded with the first reference invoice's exact data (2 × ₹61,100, 18% GST) was previewed and PDF-generated through the running app; the output was ₹1,22,200.00 / ₹10,998.00 / ₹10,998.00 / ₹1,44,196.00 — byte-identical to the client's spreadsheet.
**Migrations:** `add_customer_reference_code`, `add_line_item_hsn_sac`.

## ADR-010 | 2026-07-25 | Serverless (Vercel) support added alongside the existing Docker/self-hosted path
**Decision:** `PdfService` now detects `process.env.VERCEL` at runtime and switches Chromium sources: `playwright-core` + `@sparticuz/chromium` (a serverless-sized Chromium binary) on Vercel, vs. the full `playwright` package everywhere else (local dev, Docker — the path already verified end-to-end in ADR-008). The two PDF route handlers set `export const runtime = "nodejs"` and `export const maxDuration = 60` since Chromium needs the Node runtime and can exceed Vercel's default 10s timeout on a cold start. `next.config.ts` marks all three Playwright-family packages as `serverExternalPackages` so Next's bundler doesn't try to trace their native binaries. A `postinstall: "prisma generate"` script was added for Vercel's build pipeline (which runs `npm install` without the Dockerfile's explicit generate step).
**Why:** The user asked for this app to also be deployable to Vercel. Vercel's serverless functions have strict deployment package size limits that the full `playwright` package's ~300MB Chromium download blows through immediately; `@sparticuz/chromium` exists specifically to fit a real, working Chromium into that constraint.
**Consequences:** Two things that work for free on every other target in this document don't fully work on Vercel yet: (1) file uploads (`public/uploads/`) are ephemeral on Vercel's filesystem — logos/signatures may not survive a redeploy; (2) there's no long-running container to auto-run migrations on startup the way `docker/entrypoint.sh` does, so `prisma migrate deploy` must be run manually against the production database after each migration-bearing deploy. Both are documented in [deployment.md](deployment.md) §Vercel and [known-limitations.md](known-limitations.md) rather than silently left for the user to discover.
**Verification:** `npm run build` and the full Docker build (`docker build .`) were both re-verified after this change to confirm the existing, already-tested path (full `playwright` package, local disk uploads, `docker/entrypoint.sh` migrations) was not altered — only a new conditional branch was added alongside it. The Vercel path itself could not be end-to-end verified in this session: deploying requires signing into Vercel and authorizing the GitHub connection, an OAuth flow this agent cannot complete non-interactively (see [deployment.md](deployment.md) §Vercel step 1).
**Alternatives considered:** Ask the user to only use Docker/self-hosting (rejected — they explicitly asked for Vercel). Fully move file uploads to Vercel Blob now (deferred — real scope beyond "make it deployable," already tracked in [future-roadmap.md](future-roadmap.md) as cloud object storage).

## ADR-011 | 2026-07-25 | File uploads moved from local disk to Supabase Storage
**Decision:** `/api/uploads` (logo/signature) now uploads to a Supabase Storage bucket (`uploads`, public-read) via a new `storage.service.ts`, instead of writing to `public/uploads/` on local disk. `SUPABASE_URL` / `SUPABASE_SECRET_KEY` / `SUPABASE_UPLOADS_BUCKET` are new required env vars (server-only secret key, never exposed to the client — see [security.md](security.md)).
**Why:** Resolves the ephemeral-filesystem gap called out in ADR-010's consequences — Vercel's serverless filesystem doesn't persist uploaded files across deploys/cold starts. The user already provisioned a Supabase project (also used for `DATABASE_URL`) and an `uploads` bucket, and asked for logo/signature uploads to go there specifically so it works correctly in production.
**Consequences:** `UPLOAD_STORAGE_DIR` env var and the `app_uploads` Docker volume are removed — no longer needed on any target, including Docker/self-hosted, since Supabase Storage is now the single implementation everywhere (not just Vercel). Anyone self-hosting must set the three `SUPABASE_*` env vars even if they never touch Vercel.
**Alternatives considered:** Vercel Blob (rejected — ties storage to the Vercel platform specifically; Supabase Storage works identically on every deployment target). Keep local disk for Docker/self-hosted and only use Supabase on Vercel (rejected — two code paths for the same concern adds complexity for no real benefit, and the user's Postgres is already on Supabase).

## ADR-012 | 2026-07-25 | Raised Prisma interactive-transaction timeout for hosted Postgres latency
**Decision:** `PrismaClient` now sets `transactionOptions: { maxWait: 15000, timeout: 20000 }` globally (`src/lib/prisma.ts`), up from Prisma's defaults (`maxWait: 2000, timeout: 5000`). `vitest.config.ts`'s `testTimeout` was raised to 20000ms for the same reason — the service-layer integration tests run several sequential transactions per test against the real database.
**Why:** Discovered while acceptance-testing the Supabase Storage upload flow end-to-end (ADR-011): once `DATABASE_URL` pointed at the real hosted Supabase Postgres pooler instead of local Docker Postgres, creating a quotation failed with `Transaction API error: Unable to start a transaction in the given time.` The quotation-create transaction does numbering allocation (row lock) + document insert + line items + version snapshot as several sequential round trips; over the public internet to a hosted pooler this can exceed the 5s default, especially on a cold connection.
**Consequences:** A genuinely stuck/deadlocked transaction now takes up to 20s to fail instead of 5s. Acceptable — this app has no high-concurrency contention in MVP (single user), so the risk of a real deadlock masking a slow user-facing error is low.
**Verification:** Re-ran the failing quotation-creation request against the same hosted Supabase instance after the change — succeeded. Full test suite re-run to confirm no regression to local/Docker Postgres behavior.

## ADR-013 | 2026-07-25 | Product catalog: Category model + one-time pricelist import
**Decision:** Added a `Category` model (`id`, unique `name`) with `Item.categoryId` (nullable FK). New `/api/categories` (GET list, POST create) backs a `CategoryCombobox` on the product form that lets the user pick an existing category or type a new name to create one inline — no separate category admin screen. Separately, imported the client's real product catalog (`Standard_Pricelist_2026_V1.1.pdf`, Gunnebo India) via `prisma/data/gunnebo-pricelist-2026.ts` (323 products transcribed, one entry per category exactly matching the PDF's own section banners) and a one-time idempotent script `prisma/import-pricelist.ts`.
**Why:** User asked for products to be organized into categories (with the ability to create new ones from the product form) and for the real pricelist populated into the catalog, matching the PDF's own name/category/price structure.
**Consequences:** Per explicit instruction, every imported item has `unit = "1"` (not a real unit of measure like "pcs") and a flat `defaultGstRate = 18%` assumed for all — the source PDF has no per-product GST rate (only a footnote that GST is "extra as applicable"). If the client's actual rate differs for some products, those items need manual editing; there is no bulk-edit tool yet. `categoryId` is nullable so existing/ad-hoc items without a category keep working unchanged. The PDF's "Product Code" and "MRP" columns are not stored (not part of the current Item schema, and not requested).
**Verification:** Import script run against the real Supabase-hosted database: 18 categories + 323 items created, 0 skipped. Cross-checked totals/prices for two products against the source PDF exactly. Verified via API and browser: category filter on the products list, and the inline "Create category" flow end-to-end (typed a new name, confirmed it persisted server-side and auto-selected in the form, then removed the test category).

## ADR-014 | 2026-07-25 | Disabled vitest file parallelism to fix flaky DB integration tests
**Decision:** Set `fileParallelism: false` in `vitest.config.ts`.
**Why:** After the catalog import, full-suite runs against the real hosted Supabase Postgres started intermittently failing 1-3 unrelated test files with `Transaction API error: Unable to start a transaction`, even with ADR-012's raised timeouts — each vitest test file gets its own `PrismaClient` (module state isn't shared across worker threads/processes), so running ~15 files in parallel opens many simultaneous connections to the pooler at once, sporadically exceeding its connection limit.
**Consequences:** Full suite wall-clock time roughly doubled (tests now run file-by-file instead of concurrently). Acceptable trade — a slower but reliably-green suite beats a fast one that fails a random test on every third run.
**Verification:** Ran the full suite three times in a row after the change; 93/93 passed every time (previously 1-2 unrelated tests failed on 2 of 3 consecutive runs).

## ADR-015 | 2026-07-25 | Fixed production PDF generation on Vercel (four stacked bugs)

**Context:** The user set up the deployment at `quotepluse.vercel.app`. Checking it end-to-end (everything else — dashboard, 323-product catalog, categories, quotation/invoice CRUD, live preview pages — worked correctly against the real Supabase database) surfaced that `/api/quotations/:id/pdf` and `/api/invoices/:id/pdf` both failed with a generic 500 on Vercel specifically, despite ADR-010's serverless Chromium path never having been end-to-end verified before (that ADR says so explicitly). Vercel's error responses don't include stack details to the client, and Vercel dashboard access wasn't available at the start of this investigation, so a temporary `?debug=1` bypass was added to the quotation PDF route (and a `commit` field to `/api/health`) to surface real errors and confirm exactly which commit was live after each push. The user then set up the Vercel CLI mid-investigation, which was linked to the project (`vercel link --project quotepluse`) and used for `vercel logs`/`vercel inspect` for the rest of the diagnosis — both approaches independently confirmed the same errors.

**Four distinct bugs, found and fixed one at a time (each surfaced only after fixing the previous one):**
1. **`output: "standalone"` fought Vercel's own build pipeline.** That setting (added for the Docker image) makes Next produce one self-contained server bundle; Vercel's builder expects to trace/package each route as its own function. Running `vercel build` locally (once the CLI was available) failed outright with `Unable to find lambda for route: /invoices/new`. Fix: only set `output: "standalone"` when *not* building on Vercel (`process.env.VERCEL` is unset).
2. **Turbopack — `next build`'s default bundler as of this Next.js version — doesn't fully honor `serverExternalPackages`/`outputFileTracingIncludes` for non-code assets.** `playwright-core`'s `browsers.json` was missing from the deployed function, throwing `Cannot find module '.../playwright-core/browsers.json'` at runtime. Fix: force webpack. Critically, **editing `package.json`'s `build` script had zero effect** — `vercel inspect --logs` showed Vercel's Next.js framework preset runs its own literal `next build`, never `npm run build`. The actual fix required a `vercel.json` with `"buildCommand": "next build --webpack"`.
3. **`@sparticuz/chromium` needs to be marked `external` in webpack specifically**, per its own docs — it resolves its bundled Chromium archive via a relative path from its own file, which breaks the moment webpack touches it at all, even when already in `serverExternalPackages`. Fix: `webpack: (config) => { config.externals.push("@sparticuz/chromium"); ... }`. This surfaced a *different* file-inclusion error next (`bin/` directory missing) — same root category as #2, now for a second package — fixed by restoring `outputFileTracingIncludes` for both packages' full directories on both PDF routes (a previous attempt at this exact config had been removed earlier in the investigation because it visibly had no effect — because it was fighting Turbopack, not because the technique was wrong).
4. **`APP_URL` was set to `http://localhost:3000` in Vercel's Production environment** (the `.env.example` default, apparently copied verbatim rather than updated). Once Chromium finally launched, Playwright's `page.goto()` failed with `ERR_CONNECTION_REFUSED` trying to reach that address from inside the serverless function. Fix: removed the env var entirely via `vercel env rm` — `PdfService.appUrl()` already falls back to Vercel's own auto-provided `VERCEL_URL` when `APP_URL` is unset, which is more robust anyway (self-correct per-deployment, including previews). Also discovered and fixed in the same pass: `SUPABASE_URL`/`SUPABASE_SECRET_KEY`/`SUPABASE_UPLOADS_BUCKET` (ADR-011) were missing from Vercel entirely, meaning logo/signature uploads were silently broken in production too — added via `vercel env add`. Removed the now-unused `UPLOAD_STORAGE_DIR`.

**Verification:** After all four fixes and an env-var-refresh redeploy, both `/api/quotations/:id/pdf` and `/api/invoices/:id/pdf` returned real, correctly-rendered PDFs (verified by downloading and inspecting them) against the live `quotepluse.vercel.app` deployment. The temporary `?debug=1` bypass was removed; the `commit` field on `/api/health` was kept permanently (cheap, no secrets, useful for exactly this class of "which build is actually live" question in the future).

**Consequences (known, accepted trade-off):** A cold serverless function (no recent invocations) extracting and launching Chromium for the first time can exceed the 60s `maxDuration` ceiling and return `FUNCTION_INVOCATION_TIMEOUT` — observed directly during verification (first request after a fresh deploy timed out; an immediate retry against the now-warm function succeeded in ~10s). `vercel.json` now requests the max function memory available (1769 MB) for both PDF routes, since more memory also means more CPU on Vercel and should shorten the cold-start window, but this wasn't independently isolated/measured. A user's *first* PDF download after the app has been idle may need one retry; documented in [known-limitations.md](known-limitations.md). Raising `maxDuration` further would require a paid Vercel plan (Hobby's ceiling is 60s) — a cost decision left to the user, not made here.

**Alternatives considered:** Reverting to local-disk/Docker-only deployment and dropping Vercel support (rejected — user explicitly wants it hosted here, and three of the four bugs are now permanently fixed for any future serverless deployment target, not just Vercel). Waiting for Vercel dashboard access instead of the `?debug=1` bypass (rejected at the time — dashboard access wasn't available yet and the generic 500 gave no actionable signal; the CLI became available partway through and was adopted immediately once it was).
